# Workflow callback contract

Workflow requests carry opaque references and correlation metadata only. The API resolves tenant, action, catalog, consent, and payload data server-side. n8n credentials remain in n8n; they are not sent to the browser, Redis, or model.

The callback must authenticate the internal caller, validate tenant/action scope, execution correlation, schema version, and legal state transition. A remote CRM ID is accepted only from a verified completion response. Replayed or stale callbacks are ignored or recorded as audit events and cannot overwrite newer state.

The application claims a `dispatching` execution row before the n8n request is sent, using the action idempotency key plus event/correlation IDs. Polling claims create the `processing` action and this execution lease in one PostgreSQL transaction; a failure creating the lease rolls the action back to `approved`. A fast callback therefore has a durable target, and later acceptance cannot downgrade a terminal callback result. Workflow acceptance is recorded separately from business completion in `action_executions` and audit history; dispatching and accepted records include the durable inbox attempt and completion deadline. The watchdog reconciles an expired dispatching claim as well as an accepted execution, never blindly retrying an ambiguous CRM create.

Both callback routes use the same transition matrix. `awaiting_confirmation` can never be completed by a workflow callback. Every provider-driven `completed` or `failed` callback must carry the stored `eventId`, `correlationId`, exact execution attempt, and bounded n8n execution reference; omitted, stale, cross-attempt, cross-tenant, or mismatched claims are rejected. A late success may resolve `reconcile_required` only when it carries the same immutable tuple. The first verified callback registers the n8n reference against that execution claim. Provider terminal action and execution state are committed atomically; session workflow status and audit are written only after that commit. Terminal inbox failures are projected to the Redis DLQ from durable PostgreSQL state and are acknowledged only after that projection succeeds.
