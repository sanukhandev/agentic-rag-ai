# V2-P2-04 — Tenant-scoped Redis cache, invalidation and graceful degradation

Date: 2026-10-30  
Issue: GitHub #95  
Branch: `feat/conversation-engine-v2`

## Result

**IMPLEMENTED and verified.** The existing cache remains an acceleration layer;
PostgreSQL and durable message records remain authoritative. Cache keys used by
chat responses and catalog normalization now live under an encoded tenant
namespace. Tenant invalidation is applied after catalog/persona/source changes,
explicit consent changes, fact correction, action confirmation and provider
workflow transitions.

## Implementation

- `CacheStore.invalidate(prefix)` clears only the requested namespace in memory
  and scans/deletes matching Redis keys without using an unsafe global flush.
- `Singleflight` coalesces concurrent normalization work for the same scoped
  key; the model method is invoked with its owning object context.
- Cached response replay records a redacted `chat.cache_hit` audit event; durable
  replay records `chat.replay`. Neither path calls the model, tools or workflow
  gateway.
- Redis connection failure remains non-fatal. The bounded local fallback serves
  only short-lived values and is reconciled with Redis on the next successful
  read; health reports degraded cache status.
- Persona, catalog and source mutations invalidate only that tenant's cache.
  Corrections, consent transitions, confirmations and workflow/provider state
  transitions invalidate the same tenant namespace.

## Security and compatibility

- Tenant IDs, session IDs and message IDs are encoded in scoped keys; no cache
  value is shared across tenants by key construction.
- Audit metadata stores only a digest of the cache key, never a message, token,
  PII value or cache payload.
- The public Chat/Admin API contracts, session idempotency, consent gates,
  provider callback verification and durable state behavior are unchanged.
- Redis remains optional in development and is never treated as business truth.
