# V2-P2-02 — Transactional turn claim and idempotent chat replay

Date: 2026-10-30  
Issue: GitHub #93  
Branch: `feat/conversation-engine-v2`

## Result

**IMPLEMENTED and verified.** A client message is now claimed at the Store
boundary before session mutation, model work, tool reads or business-action
evaluation. A concurrent claimant receives the durable existing row and the
API returns `MESSAGE_IN_PROGRESS` until the owner persists a response. A
completed identical replay returns the exact saved public response; a changed
body still returns `MESSAGE_ID_REUSED`.

## Change boundary

- `MemoryStore.addMessage` now returns the existing session/client-message row
  instead of creating a second row.
- `PostgresStore.addMessage` uses `INSERT ... ON CONFLICT
  (session_id, client_message_id) DO NOTHING RETURNING *`, then reads the
  durable winner when another request claimed the key.
- The Chat API checks the row returned by the insert before updating session
  state or entering the model, tool, catalog, journey or action paths.
- Existing session revision CAS/retry logic remains the state-write boundary;
  existing action idempotency and outbox protections remain unchanged.
- No public response fields, Admin API routes, authorization checks, consent
  gates or journey rules changed.

## Evidence

The new concurrent API test holds the first model call open, submits the same
`clientMessageId` from a second request, and verifies:

- first request completes with HTTP 200;
- second request receives HTTP 409 `MESSAGE_IN_PROGRESS`;
- model draft/compose work runs exactly once;
- a later identical retry equals the first saved response exactly;
- the session contains one user message for the client ID.

The MemoryStore test verifies duplicate inserts return one existing row. The
existing API tests continue to cover changed-body conflicts, retry recovery,
action idempotency and session state CAS.
