# V2-P7-04 — Rollout, reconciliation and rollback readiness

Date: 2026-10-30  
Issue: #123  
Branch: `feat/conversation-engine-v2`

## Readiness result

Prepared the v2 rollout and rollback sign-off using the existing controls. No
feature flag was promoted and no provider write was executed.

### Rollout boundary

- `CONVERSATION_ENGINE_V2_ENABLED` must be `true` and the tenant ID must be in
  `CONVERSATION_ENGINE_V2_TENANTS`; otherwise the legacy Node path remains
  active.
- The default is disabled. The flag is tenant-scoped, not global, and is not a
  production promotion mechanism by itself.
- New sessions pin the published persona and catalog revisions. Existing
  sessions retain their durable pins; no silent catalog/persona rewrite occurs
  during a cutover.
- The public Chat API response shape and action routes remain unchanged.

### In-flight actions and rollback

- Lead, account, invoice and contract actions remain owned by the existing
  PostgreSQL action/outbox state machine.
- Redis is transport/cache only. A restart or outage does not delete state;
  outbox replay and idempotency protect dispatch.
- Callback handling requires the signed execution tuple plus tenant, session,
  opportunity, catalog, action and revision correlation. Ambiguous or missing
  provider evidence becomes `reconcile_required`, never success.
- Rollback is a configuration change: disable the v2 flag/remove the tenant
  from the allowlist and restart the API. Do not roll back applied migrations,
  delete customer history, delete actions/consents or discard provider
  callbacks. Operators reconcile in-flight actions before any retry.

### Redacted observability

The existing telemetry records bounded digests and status only: model
completion/failure/deadline/rate-limit/circuit events, v2 tool name and call
digests, guard rejection reason, provider evidence tier and stage status.
Tokens, raw PII, document contents, provider credentials and Foundry
conversation IDs are not exposed in public responses or these reports.
