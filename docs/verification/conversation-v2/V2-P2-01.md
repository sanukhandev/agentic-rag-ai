**IMPLEMENTED and focused-tested.** The additive migration and Store contract

## Safety and durability boundary

- `infra/postgres/056-user-intent-document.sql` adds only the two v2 tables and
  indexes. Existing actions, CRM leads, documents, consent records, applied
  migrations and v1 catalog history are untouched.
- The projection pins a catalog source/version reference and persona version,
  stores goal/turn/stage state, bounded masked facts with provenance, pending
  requirement/question, approved response snapshot, evidence references and
  revisions.
- The ledger is append-only by schema/API boundary, unique on
  `(session_id, client_message_id)` and `(document_id, turn_sequence)`, and
  returns the existing row for an identical replay while rejecting a changed
  message hash.
- Projection updates use an expected revision CAS. Tenant/session and
  opportunity scope are checked before reads/writes; a turn cannot attach to
  another opportunity.
- Runtime validation rejects raw email/phone/card-like values, sensitive fact
  keys such as OTP/password/secret, unbounded text/references and invalid
  revisions. No model reasoning or raw OTP field is stored.
- The public Chat API is not changed; coordinator wiring is deferred to the
  later P2/P3 tasks that consume this persistence boundary.
