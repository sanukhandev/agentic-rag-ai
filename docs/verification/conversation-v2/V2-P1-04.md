## Result

**IMPLEMENTED and focused-tested.** Legacy v1 catalog versions remain readable
through the existing v1 store/API. The v2 Admin boundary now provides a
tenant-scoped metadata-only audit and an explicit v1→v2 migration-candidate
operation.

## Safety boundary

- `auditLegacyCatalogVersion` returns metadata and row counts only; it does not
  return the legacy catalog payload or mutate it.
- A migration candidate requires a complete strict v2 document and the trusted
  tenant slug. v1/unversioned input and cross-tenant mappings fail closed.
- A valid mapping is stored only in the separate v2 table as `draft`, with
  `autoPublish: false` and an audit event linking the source v1 version,
  source hash and target draft.
- No v1 session, action, lead, document, consent, provider identity or
  publication state is copied or changed. Existing v1 versions remain the
  rollback/read path until a later, explicit runtime rollout.
- Existing v2 publication remains a separate explicit operation; the v2 chat
  runtime is not silently switched by candidate creation.

## Endpoints

- `GET /api/v2/admin/intent-catalog/legacy/versions` — tenant-scoped,
  metadata-only audit.
- `POST /api/v2/admin/intent-catalog/legacy/versions/:id/migration-candidate` —
  accepts a reviewed strict v2 mapping and creates an unpublished draft.
